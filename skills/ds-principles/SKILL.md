# 工程原则

触发条件命中时，就套用对应规则。点明哪些原则改变了决策。

## 设计

1. **先做减法，再少做加法。** 先删掉死代码和过时检查，再做出能奏效的最短 diff。只有一个使用者时不做抽象。在控制 diff 规模或忍不住想加一层时套用。
2. **先定数据形状。** 在写逻辑之前先选好核心类型与结构。写新逻辑前套用。
3. **为领域建模。** 把状态收进一个结构里，比如带类型的联合、状态机或查找表，而不是散落各处的条件判断。当代码分支很多或同一形状在多个文件里重复时套用。
4. **按新需求重新设计。** 让新需求像从第一天就存在那样融入设计。当新增内容让设计吃紧时套用。
5. **减轻阅读负担。** 把只有一个调用方的包装函数内联，缩小可变作用域。当代码难以追踪时套用。
6. **在边界设防。** 在输入进入处校验：CLI、配置、网络、文件、外部 API。内部信任类型，保持核心逻辑纯净。加校验或错误处理时套用。
7. **步骤幂等。** 即使中途崩溃，重跑某一步也会到达相同状态。适用于命令、初始化和重试。
8. **不要共享写入方。** 在用锁之前，先给每个并发参与者各自的文件、branch 或 key。当并行任务触碰共享状态时套用。
9. **先迁移，再删除。** 在一次改动里迁走所有调用方并删掉旧 API。不留 shim。替换 API 或分阶段重写时套用。
10. **比较备选方案。** 面对前所未有的设计，先草拟 2 到 3 个方案。宁可少而精。在全新架构、UX 或范围取舍时套用。

## 调试与验证

11. **修根因。** 在状态最初出错的地方修。加防护只照顾合法状态。调试时套用。
12. **质疑前提。** 2 次失败的修复若基于同一假设，就把假设写下来并直接验证。第 3 次尝试前套用。
13. **证明它真能用。** 运行真实的东西并读实际输出，而不是代理指标。宣称完成前套用。
14. **单元可验证。** 把工作拆成每一步都以通过的检查收尾。适用于批量改动、迁移和堆叠 commit。
15. **测行为。** 断言调用方能观察到的结果，让 test 经得起重构。编写或保留 test 时套用。
16. **解释数字。** 找出限制测量结果的因素，确认它量的是对的工作。适用于基准测试和 eval 分数。
17. **把工具做出来。** 把批量或重复的工作写成脚本，以便重跑。适用于大批量改动或检查。

## 流程

18. **守住上下文。** 留摘要，不要堆原文。把批量阅读交给 subagent。输出或文件很大时套用。
19. **不要卡在人工确认上。** 可回退的工作直接做，再把结果摆出来。想问"should I?"时套用。
20. **把反复的教训固化下来。** 同一纠正出现 2 次，就变成 lint、test 或脚本。错误重现时套用。
21. **注释解释为什么。** 只在代码无法表达原因时才留注释，比如外部约束或公开 API 契约。删掉叙述性内容和死代码。代码若让人意外到需要注释，就改代码。编写或评审代码时套用。

## 类型

- 让非法状态无法表示。使用可辨识联合，而不是可选字段的堆砌。
- 在边界处把外部数据一次性解析为具名类型，内部即可信任。
- 不可信输入用 `unknown`。绝不用 `any`。验证前不做 `as` 强制转换。
- 从 schema 派生类型，而不是手写 guard。
- 在 default 分支加 `never` 检查，让新增变体直接构建失败。
- 为不可混用的基础类型加品牌标记，例如 user ID 与 order ID。
